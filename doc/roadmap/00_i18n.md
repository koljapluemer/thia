# Languages: the app's, the content's, and the learner's

From the 2026-11-23 design discussion; being built (see Order).

Decided since: rewording and translating a view's text happen only in the make app, while someone makes the view;
the use app shows the wording a view was published with and nothing more (no overrides of a learner's own, no
translation a learner can set off). What a linter can enforce, oxlint enforces (`oxlint.config.ts`), and the agent's
`check` applies the same rules (`packages/check/src/i18n-rules.ts`).

The situation: the site with every view is published to the English web; the first users are teachers and students
in Germany; some views make sense in many languages (multiplication tables, in Mauritian Creole too), others belong
to one curriculum in one language; and there is no budget to machine-translate everything into n languages up front.

## Three layers, three policies

| Layer | Examples | Whose language | Translated |
|---|---|---|---|
| **The app's own text** | header, catalog, workshop, "only with views", sync | the person's | fully, up front; a small set |
| **Content** | views, decks, briefs | the content's own (`lang` on it) | per view, on demand, by tier (below) |
| **Reference data** | outlines, concept names | the issuer's | never; labelled, at most glossed |

Content has a language; people have a preference; the app's own text mediates. Most i18n trouble comes from treating
the language of content as a setting of the UI.

## Which language a page is in

**The app's text follows the person when we know them, and the content when we don't.**

- Prerendered pages and crawlers have no person: a German curriculum's page is a German page, `lang="de"`, its own
  words in German (what `Outline.tsx` does now).
- Someone who chose English gets the app's text in English once the page has hydrated (like the device's store
  shows), the outline still German inside a `lang="de"` subtree, with a badge ("Curriculum in German"). It isn't
  translated: the browser's own translation serves the occasional curious reader, as long as `lang` is right.
- The catalog shows content's language as a badge and a filter, not something to hide.
- Precedence for the app's text: an explicit choice (kept on the device) > the URL > `navigator.languages` > `en`.
  Fallbacks are per language, not always to English: `de-AT` → `de` → `en`, `mfe` → `fr` → `en`.

## URLs and indexing

- Never one URL answering in different languages by `Accept-Language`: crawlers mostly send none (so only one
  language is ever indexed), and the service worker (`web/site/public/sw.js`) caches by path.
- A language version meant to be found gets its own path (`/de/…`, or `/v/<view>/de`) with `hreflang` alternates and
  `x-default`. Content in one language keeps its one path.
- Machine translations stay `noindex` until reviewed: search engines treat scaled, unreviewed translation as spam, and
  thousands of thin `/mfe/` pages would hurt the English site.

## Views by tier

Every view records its **source language**: whatever its author or agent wrote in, often German. English isn't
assumed to be the source.

1. **Bound**: one curriculum, one class, one language. Only `lang`; never translated. Most of what teachers make.
2. **Portable**: multiplication tables, fractions, geography. Its text is in a catalog (below), 30 to 200 strings.
   Translating is one model call on the catalog, made **when someone first asks for that language**, kept for good,
   keyed by the hash of the source catalog, marked `machine` until a person marks it `reviewed`.
3. **Language is the subject**: vocabulary, transparent input. Two languages, kept apart in the data:
   - the **target language** (what is learned, `vie`): never translated
   - the **instruction language** (explanations, buttons): translated as in tier 2

   "Vietnamese for German speakers" and "Vietnamese for English speakers" are one deck with two instruction
   catalogs. The most expensive thing to retrofit, so it goes into the model first.

## A view's text as data

An agent-built view puts every string it shows in a catalog and reads it with `t()` from `@gestalts/view`. The
catalog is a gestalt (its name not chosen yet), ymls in the store, not JSON bundled with the view's code. That way
the machinery is what content already has:

- a translation is a layer of ymls with a `lang`; a person's rewording is another layer over it
- publishing carries them in the lesson's `ymls.json`; sync and merge work as for any yml
- the editor is the schema editor of [[06_deck-authoring|Deck authoring]]; a rewording view writes only this one
  gestalt, so it is an ordinary view, not app code

### Rewording without the agent

With the text as data, its author, a school or the admin team can reword a view in an editor (another view) without
an agent turn: typos, du or Sie, gender-inclusive forms, a school's own terms. The same editor reviews machine
translations. What it takes:

- **Only the view's own text is in the catalog.** Questions, answers, vocabulary, distractors are deck content. Code
  never compares against a `t()` result.
- **Keys stay stable.** An agent reworking a view is shown its catalog and keeps existing keys; after a rerun, the
  workshop lists overrides whose key is gone instead of dropping them.
- **Context per key**: the agent writes a short description for each. Better still, the frame runtime tags what `t()`
  rendered, so the editor works by clicking text in the running view.
- **Placeholders and ICU checked on save**: the same placeholders as the source, parseable; placeholders shown as
  chips that can't be edited.
- **Rendered as text**, never HTML. If Markdown is ever allowed, sanitized: overrides reach other people's devices.
- **Coverage enforced** where agent output is already checked (`@gestalts/check`): no bare strings in JSX text,
  `aria-label`, `title`, `alt`. Text drawn on a canvas or in SVG goes through `t()` too.

### Layers and staleness

Precedence: a person's override > a reviewed translation > a machine translation > the source. Each entry records the
hash of the source string it was written against; when the source changes (an agent rerun, a reworded German source
an English translation came from), what depends on it is marked stale, never silently trusted.

This is the same problem as a learner's edit shadowing a deck's yml in [[06_deck-authoring|Deck authoring]], where a
later deck update never reaches them. Solved once, for both.

Open: whom an override applies to (only me, my class or school, the published view), which decides whether it lives
in the person's store or with the published view; and that it carries over to a new version of the view (yes, with
stale entries flagged).

## Content vs. the view's text

The test, as for definitions' structural vs. presentational fields
([[../reference/data-format#Published definitions don't change|Data format]]):

- **Changes what is correct, what is practised, or which concept gets evidence → content**: a gestalt with concepts
  and versions, edited in the deck editor.
- **Changes only how it reads → the view's text**: overridable, translatable, no effect on learning data. Buttons,
  headings, generic feedback ("Richtig!"), help.

An instruction that belongs to one item ("Runde auf Zehner") is content, on the item, translatable with it.

**Translating content** is not a layer: it is a sibling deck in the other language with the same concepts. Beliefs
and practice are about concepts, and concepts are language-neutral (canonical English,
[[01_concept-naming|Concept naming]]), so a student's progress carries over between the German and the English deck
for nothing. Except tier 3, where the target language stays.

## Concept labels as a glossary

Concept ids stay canonical English and aren't shown raw. Labels per language (`{lang: label}`) make a glossary for
every translation, so "Bruch", "Kehrwert", "Nenner" come out the same in every catalog. Today other languages go in
`aliases`, which carry no language: decided together with [[01_concept-naming|Concept naming]] (2026-11-24: wait for
it, rather than a `concept@4` every concept reader would have to follow, or labels apart in a gestalt of their own).
`translateWording` takes the glossary (`Term[]`) already.

## Footguns

- **Numbers in maths views.** German `3,5` is three and a half. Decimal comma, `·` vs `×`, `:` vs `÷`, grouping. It's
  region and school convention, not only language. Parsing an answer wrong marks a right student wrong: formatting
  and parsing numbers belong in `@gestalts/view` (`Intl.NumberFormat`), not in each view.
- **The browser's translation rewrites the answers.** A student with auto-translate on gets the drill's German word
  translated into the answer. `translate="no"` on target-language content and answer keys.
- **Codes of three letters.** Mauritian Creole is `mfe`, no ISO 639-1 code. Nothing may assume two letters. CLDR
  lacks plural and date data for small languages, so `Intl` falls back to root: test one such language.
- **Hydration**: the first render in the browser is the prerender's language; switch after hydration.
- **Concatenated strings and hand-made plurals** (`` `${n} views` ``): ICU MessageFormat from the start. German and
  English hardly need it; Slavic languages and Arabic do.
- **Length and direction.** German runs about 30% longer than English: grids with fixed cells break. Right-to-left
  (Arabic, Urdu) works only with Tailwind's logical utilities (`ms-`, `me-`, `ps-`, `pe-`), not `ml-`/`mr-`.
- **Speech**: views that speak need a voice per language, which a device may not have.

## Tools

- The app's text: Paraglide JS (compiled, typed, tree-shaken per page, works with the prerender) or Lingui (ICU,
  extraction, macros). Leaning Paraglide. A lint against bare strings in JSX, and a pseudo-locale (`[Ŝéţţîñĝš ~~~]`)
  in development for hard-coded text and overflow.
- Views: simpler. Catalog ymls with ICU strings and a small formatter in `@gestalts/view`, which agents reliably
  produce.

## Order

Steps 1 to 3 cost little now and a lot later; 4 to 6 wait for demand.

1. **The app's text in `en` and `de`**, with a picker and the precedence above; `lang` attributes right everywhere,
   frames included. *Built*: `packages/i18n` (Paraglide), `/de/` with `hreflang`, `ViewInit.lang`/`locale`
   (protocol 4); lint: `react/jsx-no-literals` and the `i18n` plugin (`no-text-expression`, `logical-direction`,
   `locale-aware`). The admins' run diagnostics (`web/app/src/runs`) stay English; so do the agents' own
   availability messages (`packages/workshop/src/agents`).
2. **`lang` on views and decks**: the source language, and the target language where there is one. *Built*:
   `deck@4`, `view@4`, `lang`/`target_lang` in `plugin.yml` and lesson manifests, the catalog's language badge and
   filter, `translate="no"` on what's learned and on answers.
3. **Before many more views exist**: numbers in `@gestalts/view`; the catalog gestalt, `t()` and its check; the agent
   template's rules (only the view's text in the catalog, stable keys, a description per key). Every view built
   without them is debt. *Built*: `wording@1` (core), `t`/`formatNumber`/`parseNumber` and `resolveWording` in
   `@gestalts/view`, every plugin's text in `wording/en.yml` with a `machine` German `de.yml`, the kit's in
   `@gestalts/i18n` in the view's language; one scanner (`packages/check/src/i18n-scan.ts`) for oxlint and the
   check. Published lessons carry their wordings in `wording.json` beside the manifest.
4. Rewording: the editor view, overrides as layers, staleness. *Built, in the make app only*: the workshop's Text
   tab (`web/app/src/workshop/TextPane.tsx`, logic in `packages/workshop/src/wording.ts`) rewords a draft's text key
   by key in any language, the preview in that language, alt-click on its text to find a key; the maker's words are
   `wording-<lang>-override` and `wording-<lang>`, hidden from the agent and kept whatever it does; stale entries are
   kept or dropped, keys the agent dropped are listed. Overrides go out with the published view, for everyone.
5. Translation on demand: a catalog per language, `machine`/`reviewed`, language paths and `hreflang` for reviewed ones.
   *Built*: "Translate into…" in the Text tab, one answer from the picked agent (`translateWording`, checked per
   message, the bad ones left out and named) as `wording-<lang>-machine`; "Mark as read" moves it to
   `wording-<lang>`, which a new translation never overwrites. A plugin with a `reviewed` wording in a language of the
   app gets `/<lang>/v/<view>`, prerendered, with `hreflang`; machine-only languages get no page. No learner can set
   off a translation.
6. Content in another language as sibling decks; concept labels per language. *Built*: sibling decks (one view,
   the same `concepts`, one deck per language): the catalog shows the reader's, a view's page links the others, their
   pages name each other with `hreflang`; math-drills has a German sibling (`tools/siblings.py`). *Waiting*: concept
   labels, decided together with [[01_concept-naming|Concept naming]] (whether ids stay derived from names); until
   then `translateWording` gets an empty glossary.
